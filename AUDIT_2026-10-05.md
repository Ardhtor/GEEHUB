# GEEHUB Audit — 2026-10-05

The repository has crossed from concept into a dense interactive prototype. The main weakness is no longer lack of ideas; it is that many subsystems exist beside one another instead of forming one visual production loop.

## Immediate fixes made

- The world exception list now includes REFUSE and DRIFT, matching branches already implemented in enter().
- The filespace viewer is now initialized on startup. It previously had a complete initializer but was never invoked.

## Highest-priority work

### 1. Make media the primary substrate

The interface is still overwhelmingly HTML/CSS/Canvas. The visual-memory sections describe images/video but do not yet have a reliable persistent media manifest that the runtime consumes.

Target loop:

generation/import -> Dropbox /GEEHUB -> media manifest -> GEEHUB visual surface -> encounter -> memory -> next derivative.

The existing Dropbox bridge specification correctly says Dropbox is the durable production layer, but the browser does not directly consume that manifest yet.

### 2. Unify the many engines

The page currently loads many independent engines: fusion, corpus scry, sensation run loop, text reply, mind horizon, do-not-bother, BIGGENER, worship, mini-Blender, video realm, punishment provider, living sculpt world, hyper-morph grammar, creation registry, creation desk, and anticipation.

They should converge on a shared event/state bus rather than each inventing its own localStorage state and DOM behavior.

Canonical event vocabulary should be:

ENCOUNTER -> NOTICE -> TRANSFORM -> ARTIFACT -> MEMORY -> RETURN

Every engine can emit or consume those events.

### 3. Replace fake persistence with real asset records

window.GEEHUB_ARTIFACTS currently drives the visible artifact room, while Dropbox is separately documented as storage. The missing bridge is an actual media manifest with stable IDs, paths, dimensions, provenance, thumbnails, parent/derivative relationships, and world placement.

### 4. Make RUN consequential

RUN currently advances through a hard-coded sequence of world node IDs. It should instead select the next action from current memory, recent attention, available assets, unresolved traces, and world state.

A run should visibly alter the world and leave a durable trace.

### 5. Reduce interface sprawl

The page has many strong experiments, but the accumulated sections make the experience feel like a catalogue of features. The central visual world should become the stage; secondary engines should surface as things discovered inside it.

### 6. Video needs to become an actual world object

The repository has video-realm and self-worship-video infrastructure, but the primary visual world currently renders a procedural canvas. A media object should be able to enter the scene as video, remain visible, and become part of the world's memory.

### 7. Production pipeline

Adobe queue, Dropbox production storage, creations registry, and the visual world should share one production record. The existing engine/adobe_asset_queue.json is the natural starting point.

## Architectural direction

GitHub is the executable/canonical logic layer.

Dropbox /GEEHUB is the expanding media/world corpus.

The runtime should read a compact manifest and resolve media lazily. Large images and videos should never need to live in git.

The important transition is from:

many clever panels

to:

one world that can absorb anything the panels produce.

That is the next build threshold.
