# GEEHUB as a Narrative Jammer

GEEHUB is not only a catalog of projects. The atlas becomes interesting when it starts creating collisions between projects that would not normally be opened together.

The narrative jammer is therefore a deliberate mode of operation: instead of asking the user to decide what deserves attention, it makes a compact, interpretable surprise from the existing constellation. The surprise should feel more like discovering a strange door in a familiar building than receiving a random list.

## What a jam is

A jam takes several existing ingredients and forces them into a temporary shared scene, question, mechanism, artifact, or experiment. A useful jam might combine a world with a tool, a game mechanic with a mythic figure, an archive with a visual production method, or a research idea with a completely unrelated system.

The important part is that the collision has to produce something actionable. The output should end with something that can be made, tested, written, rendered, prototyped, or investigated.

## The desired feeling

The interaction should be playful, immediate, and slightly dangerous in the creative sense. The user should be able to press one obvious button and get a compact premise without first filling out a planning form.

The system should occasionally make combinations that are obviously strange. That is not a failure. The jammer exists partly to escape the local optimum created by repeatedly choosing the most obvious next step.

At the same time, randomness should not become noise. The project registry provides enough structure to bias combinations toward productive tension. Projects have groups, tags, summaries, and status. These become the jammer's ingredients.

## Body focus as a concrete design subject

The body is a particularly useful focus because it can connect nearly every part of the constellation without requiring a single medium. In a visual project it becomes proportion, silhouette, posture, materials, lighting, and camera language. In Beefythiq it becomes a high-girth semantic node connected to mass, volume, presence, identity, and expansion. In the Blender workspace it becomes geometry and scene construction. In fiction it becomes character and symbolism. In an archive it becomes a searchable historical motif.

A focused body-mode therefore does not need to become a sexualized interface. Its purpose is sustained formal attention: pick one physical feature or relationship, observe it carefully, alter it, exaggerate it, or translate it into another medium. This gives the user a strong anchor while preserving the open-endedness that makes the jammer useful.

The interface deliberately phrases that mode in terms such as form, proportion, silhouette, weight, surface, motion, lighting, scale, and presence. Those words are broad enough to move from anatomy to sculpture to cinematography to code while still feeling concrete.

## The basic algorithm

1. Choose a live ingredient from the project constellation.
2. Choose a second ingredient from a different group.
3. Choose a transformation verb or relationship such as "infects", "becomes", "tests", "archives", "argues with", "builds", "renders", or "escapes into".
4. Generate a one- or two-sentence premise.
5. Add one concrete action the user could take immediately.
6. Preserve the source project IDs so the collision can be traced back to real work.

The system should prefer cross-group collisions, because a system colliding with another system often produces a refinement, while a system colliding with a myth or archive can produce an entirely new direction.

## Example shape

A jam should look more like this:

> BEEFYTHIQ meets Retro Lab. Build a fake late-90s training device whose interface expresses transformation as a broken sequence of escalating UI states. The first prototype is only five screens long.

That is better than:

> Combine Beefythiq and Retro Lab.

The first version creates an image, a mechanism, an era, a constraint, and a next action. It gives the imagination something to push against.

## Narrative continuity

A jam does not replace existing canon. It creates a temporary branch. When a collision proves useful, its result can be promoted into one of the real projects or split into a new repository.

This creates a second loop inside the normal GEEHUB development loop:

**constellation → collision → premise → artifact → evaluation → promotion**

The promotion step is important. A good jammer should eventually produce durable structure, not merely an endless stream of prompts.

## Why the narrative belongs in the repository

A future developer should be able to understand why the button exists and what kind of output it should produce without reconstructing the conversation that led to it. The rationale is therefore part of the implementation contract.

The code can remain simple. The concept cannot be left implicit.

## Interface principle

The jammer should be the simplest thing in the hub to operate. The user should see a large, obvious action such as **SURPRISE ME**. Clicking it should immediately produce a premise. A second action such as **FOCUS: BODY** should establish a concrete creative anchor without forcing a single interpretation of what that anchor means. Optional details can reveal the ingredient projects and the reasoning after the surprise has already happened.

That ordering matters. The system should reward curiosity before administration.

## Future evolution

Later versions can add seeds, constraints, tone controls, continuity memory, project-specific weighting, saved jams, and a promotion action that turns a successful collision into a project brief.

The deeper goal is for GEEHUB to become a machine for making connections visible. The archive remembers. The atlas organizes. The jammer collides. The projects make the collisions real.
