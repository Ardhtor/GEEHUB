# GEEHUB — The Construction Chronicle

The chronicle is the living narrative of GEEHUB becoming a working world-making instrument. It is written from inside the construction process, not as promotional copy and not as a retrospective summary.

## Opening entry — The first machine

At first there was a clip: a body in a room, already moving, already carrying its own history. The first task was not to replace it. The task was to discover how a machine could change what happened to that body without losing the person who was there.

The first frame became a witness. The timeline became a measuring instrument. Resolve received the source and gave it a place to remain intact. Around it, GEEHUB began to construct separate spaces for evidence, growth passes, and the final image. The six marks—Baseline, Desire, Growth, Stress, Mutation, New Baseline—were not yet transformations. They were the first grammar by which a transformation could be made accountable.

The machine learned an important distinction early: arranging a process is not the same as performing it. A bin is not a body model. A marker is not a measurement. A curve is not a deformation. The chronicle keeps these distinctions visible because the world must be able to tell the difference between what it has imagined, what it has measured, and what it has actually made.

## The workshop acquires a memory

The repository became the first stable memory of the machine. Codex instructions describe how work should continue. Skills preserve repeatable methods. Resolve scripts establish the editorial room. Dropbox is designated as the exchange space for assets, evidence, bridge records, and exports. None of these rooms is the world by itself. Their connections are the beginning of the world.

GEEHUB's construction is therefore recorded as a sequence of working discoveries. Each entry should identify the artifact created, the capability it actually provides, the evidence that it works, and the next unresolved operation. The story must advance when the machine advances; it must not invent progress to make the story sound complete.

## The governing image

A frame is a surface carrying evidence of a body. A sequence is a body changing through time. A world is the set of relations that makes that change legible: joints, silhouette, weight, fabric, floor, walls, camera, light, sound, and the people who recognize the subject.

The intended sensation is escalation with continuity. Scale may become startling; identity must remain. Growth should be felt in the whole scene, not merely in a swollen patch of pixels. The room may become too small. Fabric may pull. The camera may need to look upward. Yet every consequence must arise from a coherent state, not from arbitrary distortion.

It gives the source clip an immutable identity, then records measured frame sets, render-job references, output destinations, and the artifacts that eventually return. Each change creates a new revision and leaves an event behind, so a later worker can tell which state it received and what happened after it.

Its job JSON and rendered output have separate exchange paths. The manifest reserves those paths, refusing collisions with source footage or other frame assets. A running job may finish only by returning an artifact at its reserved destination with a caller-supplied SHA-256 digest; the manifest checks its format but does not read the output bytes. Failure remains a recorded failure; it does not become an empty success.

## 2026-11-02 — The bridge can be inspected from the editing room

The instrument does not touch the timeline. It does not import footage or start a render. When a queued job's JSON agrees with the manifest and its reserved output path is unused, the audit labels it ready-for-local-renderer. That phrase is deliberately modest: it means the handoff is intelligible and the destination is clear, not that the renderer has executed. The audit is written to the Bridge outgoing folder, with a Desktop fallback.

## 2026-11-03 — The courier writes the first local envelope

A new instrument has been added beside the manifest: core/bridge-exchange.js. It gives the versioned exchange a local filesystem edge. Dropbox URIs are resolved beneath the configured root; traversal, encoded path tricks, and symlinked exchange directories are refused before any handoff is written. The source clip must exist as a regular file. Its bytes are read for a SHA-256 digest, and when the manifest already declares a digest, the actual file must match it.

The staging pass checks the portable job again at the point of delivery: source dimensions and duration, output dimensions and frame rate, the presence of growth states and landmark frames, and the face, source-motion, ground-contact, connected-mesh, and temporal-stability constraints. It reserves four distinct destinations—the source, job JSON, manifest, and future render output. Existing manifest, job, or output files are never replaced. The job is written first; the manifest is written last, so the Resolve inspector cannot discover the exchange before the job file is complete. If the manifest write fails, the newly created job file is removed.

The command-line entry is tools/stage-bridge-exchange.js, exposed as npm run stage:bridge. A successful run prints a receipt containing the actual source digest and the digests of the staged job and manifest. The output path is reported but not created. This is the first filesystem-backed courier, not a frame renderer: it does not segment a body, deform an image, create a video, or touch the user's Dropbox from this repository session.

## 2026-11-04 — The frame-sequence bench receives its first inspection instrument

The workshop now has a frame-sequence intake contract and a local file inspector. The contract does not reorder its evidence to make a damaged sequence appear orderly. Frame numbers must arrive contiguously; timestamps must follow the declared frame rate; every observation must point back to the same immutable source and preserve the source dimensions. The track carries both the articulated body anchors and the smaller set of facial identity anchors. Confidence, missing joints, abrupt motion, and timing gaps are all visible before geometry is allowed to proceed.

The segmentation producer leaves two separate references at each frame: a body mask and a face mask. Their paths must be unique, their declared dimensions must match the source, and each carries a SHA-256 digest. The body-mask record declares that it excludes the face; the face-mask record declares that it protects identity. Those declarations are not mistaken for proof. The local inspector follows each Dropbox URI beneath the configured root, refuses symlinked paths, hashes the actual file bytes, and reads the PNG signature and IHDR dimensions. Only a structurally complete sequence whose mask files pass those checks is labeled ready-for-geometry.

Seven focused tests passed under Node 22.16.0. They include a complete two-frame sequence, deliberate frame reordering, source and dimension mismatch, a landmark-only sequence awaiting segmentation, identity loss, abrupt landmark motion, real PNG checksum and dimension checks, checksum mismatch, and symlink refusal. Syntax checks passed for the two core modules and the command-line inspector. The command is exposed as `npm run inspect:frames`.

This instrument is a gatekeeper, not a sculptor. No segmentation model ran. The worker does not decode mask pixels or prove that a declared face-excluding mask actually excludes the face; it does not create a mesh, deform an image, or render a clip. It has not been run against the user's Dropbox mirror or Resolve session. Its evidence is local test evidence only.

The next passage connects the inspected sequence to the bridge manifest's typed frame sets, so the same verified segmentation and landmark records can become explicit inputs to a render job without losing their source lineage. After that, the workshop still needs a real segmentation producer and a mesh whose triangles remain stable from frame to frame.

## 2026-11-05 — The measured sequence enters the bridge

The frame-sequence bench can now hand its verified measurements to the numbered envelope. A new adapter accepts the source-matched sequence and the local mask-file audit, then prepares two distinct sidecar records: one for segmentation and one for landmarks. The first preserves the per-frame body and face mask references, their checksums, the segmentation producer, and its confidence. The second carries the face and body landmarks with identity and pose confidence. Both records retain the same source, frame range, dimensions, frame rate, and sequence identity. Their exact JSON bytes are hashed before the manifest receives the corresponding typed frame-set entries.

The queue has become stricter. A render job can no longer be admitted with a loose landmark array and no segmentation record: it must name exactly one segmentation frame set and one landmark frame set, and those two must describe the same sequence and the same temporal and spatial format. The Resolve inspector applies the same rule when it reads the envelope. At the local exchange bench, the courier now opens each referenced sidecar, refuses missing or non-regular files and symlinks, hashes the actual bytes, and compares them with the manifest before it writes the job and envelope. The returned receipt lists the files it verified.

The adapter returns the exact sidecar contents and their intended Dropbox URIs; it does not write those documents itself. The next local instrument must persist them safely before staging. The file audit still proves only that the PNG headers, dimensions, and bytes match their declared checksums. It does not inspect mask pixels, establish that the body mask truly excludes the face, or generate geometry. No Dropbox mirror or Resolve session was accessed during this construction pass, and no frame was deformed or rendered.

## 2026-11-06 — The measured evidence is written into the archive

The two records prepared by the frame-sequence adapter no longer need to remain in memory or be copied by hand. A new registration instrument, `core/frame-sequence-registration.js`, takes the segmentation and landmark sidecars and checks them against the manifest that will own them. It confirms the source and sequence identity, the frame range, dimensions, frame rate, role, and the digest of the exact JSON bytes. A record that has been changed after preparation cannot pass through the door.

The instrument writes into a revisioned shelf beneath the local GEEHUB Dropbox mirror. It creates each sidecar exclusively, reads the file back, and calculates its checksum again. Only after both sidecars agree with their declared digests does it write the new manifest revision. Existing files are left untouched. Symlinked directories are refused. If a later step fails, cleanup is limited to files created by this run whose contents still match the expected digest. The command `npm run register:frames` repeats the mask-file inspection before registration, so it does not rely on a stale audit document.

## 2026-11-07 — The measured sequence becomes a queued job

The registration shelf now opens onto a workbench where a measured sequence can become a specific render instruction. The new instrument, `core/bridge-render-job.js`, reads the exact segmentation and landmark sidecar text that was written during registration. It does not trust the filename or the fact that a sidecar exists. It hashes the bytes again, checks the schema and role, confirms that the source and sequence identifiers match the manifest, and compares the frame range, dimensions, and frame rate. Frame numbers must arrive in order, timestamps must increase, and the two sidecars must describe the same moment at every index.

The segmentation record carries the separate body and face masks forward with their checksums. The body record must still declare face exclusion; the face record must still declare identity protection. The landmark record must contain the articulated anchors and the facial anchors used to preserve recognition, with normalized coordinates and sufficient confidence. These declarations and measurements are kept distinct from proof of pixel semantics. The payload therefore carries an explicit `pixelSemanticsVerified=false` rather than allowing a well-formed JSON record to masquerade as a verified mask.

The approved growth states pass through the existing cumulative-state validator and then become part of a portable render job. Its new `frameEvidence` record points to the exact segmentation and landmark frame-set IDs, their checksums, their sequence, and their common frame format. The bridge queue refuses a job if that record differs from the registered evidence. The local courier repeats the comparison before staging, and the Resolve inspector now checks the same references when it audits the incoming job. The landmarks are carried in the job; the segmentation sidecar remains a separate immutable input that the renderer can locate through the manifest.

A new local command, `npm run prepare:render`, reads the registered manifest and its two sidecars from the configured Dropbox mirror, combines them with a JSON file of approved growth states, and writes a new queued manifest and job JSON into a bundle directory. It uses exclusive file creation and publishes the manifest only after the job file is complete. The receipt gives the next `stage:bridge` command, so the two operations can be performed in sequence without manually assembling the job envelope. Multiple registered sequences must be selected explicitly. The render-job format now also preserves fractional frame rates such as 23.976 instead of forcing them to an integer.

## Chronicle rule

Do not turn missing capabilities into lore that disguises their absence. The narrative is the machine's construction record, and the construction record is part of the machine.
